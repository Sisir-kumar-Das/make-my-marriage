# ADR-052 — Wedding deletion and seven-day recovery

Date: 15 November 2026

Status: Sisir approved implementation after discussion. Verification and owner acceptance are separate in PROJECT_STATUS.

## Approved flow

Use the corrected Settings lifecycle danger card, typed DELETE confirmation and recovery terminal. Only current verified active Admins can delete or restore. Recovery ends exactly seven elapsed days after deletion, displayed in India time; expiry is checked on the server, not trusted from a client countdown. Other current eligible members see the same recovery terminal without Restore and with “An Admin can restore this wedding.” Accounts and personal profile photos survive wedding deletion/purge.

Keep ACTIVE memberships reserved until restoration or completed purge, blocking new wedding creation/joining in accordance with the one-active-wedding index. Cancel all PENDING invitations atomically when deleting; old links never reactivate on restoration. Existing accepted members return with their saved permissions. Preserve tasks, ceremonies, individual deletion flags, repeat schedules/cursors, checklist identities and history during recovery. Existing repeat authorization pauses generation while the wedding is deleted; after restoration the existing bounded catch-up rules apply without rescheduling saved dates.

Deletion/restoration use current account/member locks, If-Match and actor/wedding/purpose/body/version-scoped 24-hour receipts in one transaction with the root change, invitation cancellation and hidden audit. Authorization precedes receipt replay. Replay returns current state, never re-deletes a restored wedding or restores a later deletion. No-op or repeated actions with fresh keys must not extend the deadline. At most 1000 pending invitations may be cancelled in one transaction; larger deletions fail without partial writes.

Normal session data returns only a minimal recovery summary for a deleted reserved wedding, not normal wedding details/budget. Both workspace SSR/RSC guards and client session recovery redirect to the fixed `/wedding-recovery` route, which is outside the normal workspace. Removed, disabled, unverified or unrelated users cannot inspect recovery. Preserve in-memory exact operations through uncertain errors and lock pending confirmation/actions. No automatic destructive action on navigation.

## Purge boundary

Only an expired, still-deleted wedding may be claimed for purge; once expiry is reached restoration is forbidden even if the worker has not run. Renew a lease, process bounded wedding-owned media/child batches, then release memberships and delete the root last. R2 deletion must succeed before its metadata is removed. Use the existing environment-scoped storage adapter; never delete account-owned PROFILE_AVATAR data. Retry failures idempotently and expose pending/in-progress cleanup honestly. Do not infer successful purge from expiry or a missing record.

An executable bounded purge command is included for the approved runtime's scheduler. Local Express scheduling may invoke the same worker. Durable deployed scheduling, restart/catch-up, overlap/retry behavior and failure visibility remain mandatory deployment prerequisites; this increment neither deploys nor selects hosting. Keep recoverable data until actual cleanup finishes, with no MongoDB TTL on wedding roots/children. No public endpoint for forcing an early purge.

## Presentation

Settings lifecycle uses the reference card and typed confirmation. Recovery renders only the applicable real state rather than the reference's simultaneous demo/gallery cards. The owner approved the non-Admin restore explanation, reserved membership policy and invitation cancellation. An expired-but-not-yet-purged state must say cleanup is pending/in progress, not that data is already erased. Global account/logout access remains available. Exact retries and reload errors use existing accessible feedback patterns, without new dependencies or browser storage.

## Uncertain save result confirmation — 19 November 2026

Sisir observed a client timeout followed by eventual deletion and restoration. He approved preparing lifecycle receipts before first use, a 15-second lifecycle save budget and automatic read-only confirmation of an uncertain result. The original seven-second Atlas slowdown is not attributed to a particular database event: local initialization probes did not reproduce it. The confirmed five-second client/default mismatch and uncertain-outcome handling are addressed separately.

Include WeddingLifecycleRequest in the shared connection's awaited model initialization, preserving connection reuse, failed-opening cleanup and shutdown semantics. Delete/Restore retain their existing transaction, locks, audit, If-Match and 24-hour receipts. Their browser request budget is 15 seconds, within the existing 20-second relay budget; a client deadline never claims to cancel or roll back a server transaction.

The protected POST /weddings/:weddingId/lifecycle/result is read-only despite its POST transport: the original key/body must not enter a URL. Require current session, trusted Origin, JSON, signed CSRF and a separate bounded allowance of 60 lookups per account per 15 minutes. Validate a strict action/body envelope, original If-Match and original Idempotency-Key. Within one read-only snapshot, recheck the verified active account, eligible membership, existing wedding and current Admin role before inspecting that actor/wedding/key's unexpired receipt. Match its purpose/action, version and canonical body hash. A matching receipt returns confirmed: true plus CURRENT minimal lifecycle state, respecting any later Admin restore/delete; it never repeats the write or returns private receipt contents. Absence/expiry returns only confirmed: false, which means unconfirmed, never failed, cancelled or not started. No root/member/account lock counters, receipts or audits are written by this lookup.

For an uncertain write response, retain the exact in-memory operation and show “Checking deletion result…” or “Checking restoration result…” in the existing feedback area with status semantics. Keep pending controls and dismissal locked. Perform at most three lookups, immediately then with 1.5- and 3.5-second gaps, using a five-second budget per read. A failed read stops automatic checking. A confirmed result uses the existing fixed navigation based on current state; a missing/malformed/unavailable result keeps the original operation and says the result could not be confirmed and may still complete. The existing Retry resubmits only that exact original operation. No automatic new Delete/Restore is sent.

Recognized current access loss (SESSION_EXPIRED, ADMIN_REQUIRED, EMAIL_NOT_VERIFIED or WEDDING_NOT_FOUND with the matching HTTP status) follows the approved scope/denial handling. A generic missing result endpoint or other lookup error does not prove loss of access or failure of the write, so it must preserve the operation. Existing expiry events, unmount/scope sequencing, session-outage draft preservation and navigation locks remain. Abort result reads/delays on unmount and ignore stale callbacks, mismatched wedding DTOs or confirmed account changes. The new checking/unconfirmed copy reuses the existing dialog/page feedback without new controls or layout. See STITCH_DEPARTURES #21 and PROJECT_STATUS for verification and owner acceptance.

## Rate-limit feedback — 20 November 2026

Sisir approved accurate feedback when the lifecycle write route returns HTTP 429 RATE_LIMITED. Skip automatic result lookup for the blocked attempt and use the server's Retry-After wait in the existing alert when available. A blocked first attempt releases the operation, keeps the typed DELETE confirmation while the dialog stays open, and enables dismissal. A blocked Retry retains the prior uncertain operation with the same body, If-Match and key, and explains that its earlier outcome remains unconfirmed. The server enforces the existing allowance. A rate limit on the separate result route remains an unavailable lookup and preserves the operation.
