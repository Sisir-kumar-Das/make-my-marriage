# ADR-033: Task deletion and original-creator recovery

Date: 26 October 2026

Status: Owner approved permissions and implementation. Actual verification and pending acceptance belong in PROJECT_STATUS.md.

## Owner decision and scope

The owner confirmed that Admins and Family Members may delete tasks, and approved restoring any task for Admins versus only tasks they originally created for Family Members. A Family Member deleting someone else's task does not gain restoration rights. Viewers remain read-only, including tasks they previously created before a role change or are currently assigned. This resolves the API baseline's Admin/creator restore policy; Admin-only whole-event deletion/restoration stays unchanged under ADR-027.

Deliver soft deletion from the existing Stitch task drawer and real deleted-task rows in the Settings Data Recovery Tray. Preserve its typography, surfaces, layout and responsive actions. The reference's global Admin Exclusive badge must reflect the approved task exception: role-based recovery, with separate Admin-only event and creator-scoped task guidance. The wedding's seven-day recovery period is separate: no seven-day task expiry or permanent task purge is introduced. Removed tasks remain recoverable while their active wedding exists. Whole-wedding lifecycle, dashboard shortcuts, ceremony task integration and checklist generation retain their scheduled later increments.

## Backend rules

- DELETE `/weddings/:weddingId/tasks/:taskId` marks deletedAt/deletedBy and updatedBy, increments the task version, and preserves notes/status/completion/priority/deadline/assignees/ceremony/source/history. No cascade or permanent erase. Normal task lists, My Tasks, counts, filters, reads, edits and series entry exclude deleted tasks.
- GET `.../tasks/deleted` is a strict bounded paginated recovery read, sorted by deletion date/ID and clamped after changes. GET `.../tasks/:taskId/recovery` reads a removed record. Admins see all removed tasks in the active wedding; Family reads are constrained by createdBy=the authenticated actor. Viewer access is rejected; foreign, active or unauthorized IDs are not disclosed. No browser-supplied creator/scope override.
- POST `.../tasks/:taskId/restore` applies the same current-role/creator check, retaining the exact saved task details. Retain unavailable assignee/ceremony references and identify them neutrally, without disclosing stale member names or unavailable ceremony details. Later editing requires the existing explicit unavailable-assignee repair. Never silently assign a new member, change completion or restart a pattern during restoration.
- Recheck active verified user, current active membership/role and active wedding for every read/mutation/retry. Use existing account/member/wedding transaction locks so concurrent edits, permission changes and recurrence reconciliation cannot overwrite lifecycle changes. The role/creator restriction is enforced in Express, not merely by hiding controls.
- Both mutations accept only an empty object with trusted Origin, JSON, CSRF, rate limits, a UUID Idempotency-Key and current task If-Match. Store account/wedding-scoped hashed 24-hour receipts. Exact retries acknowledge current state after intervening restoration/deletion; never reapply an older action. New stale versions or wrong-state requests conflict. Preserve explicit review/refresh before a new action. Keep task/receipt/TASK_DELETED or TASK_RESTORED history writes atomic, with retained activity labels. No sensitive request bodies enter audit metadata.

## Recurring copies

Delete only the selected dated copy. Keep its unique series/date identity so background generation cannot recreate it. Other copies and future generation continue; Stop future generation remains a separate existing action. Deletion/restoration marks a series copy individually edited. Explicit restoration preserves that copy's original saved details even if the future pattern changed while it was removed, and does not reactivate a stopped pattern. Pattern-retired untouched dates (recurrenceExcluded) do not appear as user-deleted tasks in Recovery. Ordinary deletion cannot target an already retired copy; explicit restoration returns a genuinely deleted copy to the normal list.

## Frontend and recovery

Use Stitch's fixed-footer confirmation naming the task, with Cancel deletion and Confirm delete task. Recurring copies explain the one-copy scope; unsaved edits explain that deletion discards the draft. Keep the prompt visible when the form body is scrolled. Bound and independently scroll the header, footer and confirmation text so a valid 160-character title at 320 px cannot push Cancel/Confirm out of reach. Drawer headings use the corrected Stitch section-title style (Inter, 20 px, weight 600); the main page heading stays separate. Cancellation retains entered values. Pending saves/removals block dismissal, discard, duplicate submission and other edits. Failed deletion retains the original key/version for retry; conflicts require explicit loading/review. On success close the drawer, refresh real counts/list pagination and offer Deleted Items Recovery.

Extend the existing recovery page with a task section containing real names, deletion time/actor, status/priority/deadline, eligible assignees, retained ceremony reference, saved notes disclosure and Restore Task. Viewer/Family explanations reveal no unauthorized removed records. Family scope is labeled separately from event permissions. Restoration shows confirmation, optional deadline/unavailable-reference guidance and View Tasks. In both the task and future-repeat editors, move focus and scroll to the inline connection notice when a background session check fails, so Retry is visible above a scrolled draft without discarding its values. Preserve task retry identities across transient API/session errors on `/recovery`, while confirmed invalid sessions still block access; retain both SSR guards. Failed/stale list requests hide old rows and offer Retry. A last-page restoration clamps the recovery list. No fake rows, permanent-delete control or new dependencies/credentials are introduced.
