# ADR-043: In-app invitations and shared Accept/Reject decisions

Date: 30 October 2026

Status: Owner explicitly authorized this Members follow-up after discussing both entry points, single use, concurrent decisions and fresh invitations after rejection. Live Dashboard remains next after Members acceptance. No agent coordination, Git handoff or deployment is authorized.

## Scope and interface

Enable Stitch wedding setup's Accept Invite entry and add My Invitations to the account menu. Authenticated verified recipients can browse bounded pending invitations for their own normalized email and review wedding, issuer, role, relationship and expiry. Reuse the corrected recipient acceptance card, plum palette, Playfair heading and existing responsive controls. The new recipient list is an owner-approved extension; the baseline PRD describes an email-link journey, not an invitation inbox. Preserve the approved baseline files.

Email provides Accept and Reject buttons opening the same review page. Links only navigate: no GET, link scan, fragment intent or email verification can decide membership. Sign-in/registration and matching verified email remain mandatory. Explicit Reject opens a confirmation; it never deletes an account or changes existing membership. In-app decisions do not require opening Gmail or exposing/reconstructing tokens. Existing token acceptance and fixed auth continuation remain compatible.

## Shared lifecycle

Both entry points consume the same MemberInvitation. The first valid transaction committed wins: PENDING becomes ACCEPTED or DECLINED. Expired/revoked invitations cannot be decided; unavailable invitations cannot be accepted but can be rejected (owner decision, 1 November 2026, below). Accepted/declined invitations leave the recipient pending list; old links show their terminal state without another action. Refresh on focus, periodic checks and an invitation-change browser channel update stale views, but Express remains authoritative even before refresh. Keep Admin history read-only for terminal records. A declined record never reopens or resends; Admin can explicitly create a fresh invitation/new token for that email. Prevent new/resend mail to an active member of the same wedding. Preserve seven-day expiry, resend rotation/cooldown and current issuing-Admin checks.

## API and storage

GET `/member-invitations/inbox` and `/inbox/:id` require a current active verified account, scope reads to its server-owned email, return minimal metadata and no nonce/token/hash/receipt/other recipients. Recipient pending queries have their own index. Owner-approved declines add DECLINED, declinedAt/declinedBy and immutable INVITATION_DECLINE audit. No raw token is stored. ID-based Accept/Decline uses a reviewed version; token decisions require the current token generation. Decline requires explicit confirmation.

Both routes share the existing transactional write service, current account/wedding/issuing-Admin locks, CSRF/Origin/JSON boundaries, strict input and 24-hour exact receipts. Acceptance preserves one active wedding and creator/relationship rules; decline creates no membership. Receipts are reauthorized before replay and never send mail, reapply membership or reopen old decisions. Concurrent Accept/Reject or app/email actions serialize on the same account/invitation; the losing action receives the saved terminal state. A lost response retains its original operation/body/key in React memory; do not permit the opposite action while its outcome is uncertain. Refresh can discover a committed terminal state. Preserve pending dismissal locks, transient-error recovery and stale response cancellation; no browser storage or new state dependency.

Review clarification, 30 October: the browser API client preserves the HTTP response status alongside its application error code. Only a recognized terminal 4xx decision response may clear the saved attempt; 5xx/network/unknown outcomes retain its exact action/body/key, including when a fresh preview remains PENDING. The shared INVITATION_UNAVAILABLE code alone cannot distinguish a closed invitation from a temporary service failure. Completed feedback belongs to its confirmed actor, stays hidden while identity is rechecked and clears when a different account or logout is confirmed. Empty-inbox guidance respects the current one-wedding context.

Owner decision, 1 November 2026 (supersedes "unavailable invitations cannot be decided" for Reject only): when the issuing Admin is no longer a current eligible Admin or the wedding is gone, a still-PENDING invitation can be **rejected but never accepted**, so the recipient can clear it. Recipient reads return state `UNAVAILABLE` with `canReject`, the invitee email and expiry only (no wedding, issuer or role details); the review page and My Invitations offer a Reject-only action with the same confirmation. Decline therefore skips the issuer/wedding availability check and lock; Accept keeps them unchanged. Concurrent decisions still have one winner through the invitation's optimistic version. An unconfirmed Accept attempt is discarded once the invitation is confirmed UNAVAILABLE (a committed accept would read ACCEPTED), so Reject is not blocked. Each page ignores its own invitation-change broadcast while other tabs still refresh. All other ADR-043 rules, including hidden completion feedback during identity rechecks, are unchanged.
