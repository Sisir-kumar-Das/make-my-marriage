# Make My Marriage project instructions

- Work in this existing npm-workspace repository: `apps/web` and `apps/api`, JavaScript/JSX, ES modules, Node.js 24, npm, one root lockfile.
- Read the relevant approved documents in `docs/` before implementing a feature. Preserve their contents and all pre-existing user changes. Record superseding architecture decisions in `docs/decisions/`.
- Read `docs/PROJECT_STATUS.md` at the start of work to understand completed milestones, current limitations and the next development step. Check the actual code and Git status before continuing; the status file does not replace the approved requirements or architecture decisions.
- After each major feature or milestone, update `docs/PROJECT_STATUS.md` in the same handoff with the date, delivered scope, relevant files/decisions, verification results, remaining work and next step. Keep completed work separate from sample data, placeholders and planned features. Fold small follow-up fixes into the existing milestone instead of creating a milestone for every edit.
- Follow the agreed feature sequence in `docs/PROJECT_STATUS.md`. Before starting work in a different order, tell the owner what changed and why, and record the revised sequence there so their personal notes and future agent handoffs stay consistent.
- Keep business rules, authorization and database access in Express. Web code uses `apps/web/src/lib/api-client.js`; it must never import API source/models or connect to MongoDB.
- Follow `docs/decisions/ADR-016-frontend-state-management.md`: local React state, existing session Context and React Hook Form/Zod are the current approach. Redux/Redux Toolkit and TanStack Query are not selected or installed; revisit only for a concrete feature need and record the decision before adding a state-management dependency.
- Use explicit application routes. Prefer ordinary components/functions and useful files; do not add empty module trees, shared packages, repository abstractions or monorepo build tools without a concrete need.
- Follow ADR-038 for homepage session recovery: bound checking and workspace opening, use one fixed same-origin document replacement, stop a stalled load before showing Retry/Continue, and revalidate on Retry. Cookie hints never authorize access; only confirmed expiry reveals the public homepage. Preserve both workspace guards, reject stale attempts and keep the scoped root-entry fix separate from direct-route recovery and draft preservation.
- Members Step 1 is implemented under ADR-039: current eligible wedding directory, all-role filters, bounded pagination and real open-task counts (To Do/In Progress, including overdue; exclude completed/deleted/retired; shared tasks once per assignee). Email is returned only to current Admins or that account owner. Relationship tags belong to membership, never permissions: the original wedding creator is exempt, later members including Admins require a relationship when invitation/membership writes are implemented. Nullable legacy storage is read compatibility, not permission to omit required labels in future acceptance. Do not guess/backfill relationships. See ADR-040 for the invitation increment; role changes, member removal/reassignment and their last-Admin protections remain later increments with disabled honest previews. Keep existing assignee-picker contracts and both SSR/RSC guards.
- Members Step 2 invitations are implemented under ADR-040: only current verified active Admins create/list/copy/resend/revoke; Family Member is the default. Require a common relationship or Other with a non-empty custom label. Gmail uses the existing private sender. Store only a token hash plus random nonce; purpose-separated server HMAC reconstructs Copy Link without plaintext token storage. Links live in fragments, expire after seven days and rotate on resend with a 45-second persisted cooldown. Keep invitees out of member/assignee counts until a matching verified account explicitly accepts. Preserve invite context through login/registration/verification, including another tab, using fixed routes without browser storage or arbitrary redirects. Acceptance is atomic, audited, duplicate-safe and respects one ACTIVE wedding; revalidate account/wedding/current issuing Admin before joining. Recheck authorization before replaying 24-hour receipts; never resend email or restore removed access from a replay. Uncertain dispatch is visible and must not claim inbox delivery. Preserve Members drafts/keys during recoverable session errors and lock pending modals. Role/removal management and deployment remain later scope.
