# Make My Marriage project instructions

- Work in this existing npm-workspace repository: `apps/web` and `apps/api`, JavaScript/JSX, ES modules, Node.js 24, npm, one root lockfile.
- Read the relevant approved documents in `docs/` before implementing a feature. Preserve their contents and all pre-existing user changes. Record superseding architecture decisions in `docs/decisions/`.
- Read `docs/PROJECT_STATUS.md` at the start of work to understand completed milestones, current limitations and the next development step. Check the actual code and Git status before continuing; the status file does not replace the approved requirements or architecture decisions.
- After each major feature or milestone, update `docs/PROJECT_STATUS.md` in the same handoff with the date, delivered scope, relevant files/decisions, verification results, remaining work and next step. Keep completed work separate from sample data, placeholders and planned features. Fold small follow-up fixes into the existing milestone instead of creating a milestone for every edit.
- Follow the agreed feature sequence in `docs/PROJECT_STATUS.md`. Before starting work in a different order, tell the owner what changed and why, and record the revised sequence there so their personal notes and future agent handoffs stay consistent.
- Keep business rules, authorization and database access in Express. Web code uses `apps/web/src/lib/api-client.js`; it must never import API source/models or connect to MongoDB.
- Follow `docs/decisions/ADR-016-frontend-state-management.md`: local React state, existing session Context and React Hook Form/Zod are the current approach. Redux/Redux Toolkit and TanStack Query are not selected or installed; revisit only for a concrete feature need and record the decision before adding a state-management dependency.
- Use explicit application routes. Prefer ordinary components/functions and useful files; do not add empty module trees, shared packages, repository abstractions or monorepo build tools without a concrete need.
- V1 covers auth, wedding setup, events, tasks/recurrence, checklist templates, members/invitations, dashboard/activity, profile/settings and recovery. Later-version designs are compatibility plans, not scaffold scope.
- Authentication, basic wedding setup and private wedding cover uploads are implemented; consult `docs/PROJECT_STATUS.md` for validation/configuration status. Workspace entry requires a verified session and active wedding membership, with both layout and page-level SSR/RSC guards preserved. The dashboard uses real wedding details and planning empty states; Events Step 1 implements ceremony create/list/details/edit with manual venues; filters/activities/deletion/Places and tasks/invitations remain deferred. Follow ADR-023 for tenant/role enforcement, India-time schedules, transactional history, versioned edits and 24-hour idempotent saves. Google Places remains required before closing Events/V1. See ADR-017 for atomic wedding/Admin creation, the one-active-wedding rule and idempotent retries. Follow ADR-020 for optional 15 MB JPG/PNG covers, non-destructive framing, account-owned setup media, atomic attachment, Admin replacement/removal and bounded cleanup. The owner requires the same private R2 account/bucket for dev/prod with generated `dev/` and `prod/` prefixes; credentials remain server-only. Password reset still transactionally revokes all account sessions; preserve generic forgot responses and ADR-015's local dispatch boundary. Preinstalled dependencies do not imply implemented features.
- The corrected Stitch HTML in the ignored `stitch_make_my_marriage_landing_page_v1_final/` export is the current visual source of truth; see ADR-021 for the route/reference mapping. Use `design/reference/` if references are supplied there later. PNG previews may be stale. Match the applicable reference's layout, logo placement, colors, fonts, spacing and responsive behavior for every page; discuss intentional visual departures with the owner before implementing them. Unbuilt features retain reference-shaped previews with disabled controls and visible Coming soon labels, never fake live records, progress or security claims. Preserve the complete approved M logo, the chosen local brand artwork and actual member permissions. Reference/gallery demo controls are not product functionality.
- Keep environment examples credential-free. Never commit secrets, local environment files, build output or `node_modules`.
- Follow ADR-018 for Gmail SMTP on this small personal project. Express selects `EMAIL_PROVIDER=gmail` or `resend`; Gmail uses private `SMTP_USER`/`SMTP_APP_PASSWORD`, derives the sender from that account and never falls back automatically to Resend. Consult PROJECT_STATUS.md for actual inbox/database validation; an authenticated SMTP connection alone does not prove delivery. Preserve verification/recovery security and generic resend/forgot responses when changing the backend email adapter. ADR-019 records the owner's explicit exception for duplicate registration: HTTP 409 `EMAIL_ALREADY_REGISTERED` leads to login without sending mail or changing the account, deliberately revealing email registration existence. ADR-022 extends that owner-approved disclosure to login: a missing account returns HTTP 404 `ACCOUNT_NOT_FOUND` and opens registration with an explanation; existing wrong-password/disabled responses remain generic and verification is still required.
- Local development is authorized. Deployment is deferred; Amplify support for Next.js 16 is unresolved. Do not change hosting providers.
- Do not reset, discard, move existing documents, commit or push unless explicitly instructed by the user.
- Before handing off changes, run applicable checks: `npm run lint`, `npm run format:check`, `npm run build`, and `npm run smoke` against running applications. Verify independent/combined startup, production web startup, browser API connectivity/unavailable states and desktop/mobile navigation. Report checks that could not be performed.
- Add tests when they protect meaningful behavior; do not install a test framework merely for the scaffold.

See `docs/PROJECT_STATUS.md` for progress, and `README.md`, `docs/DEVELOPMENT.md` and `docs/decisions/ADR-011-npm-workspace-monorepo.md` for setup and boundaries.
